## 1. 检查目标

本检查不以“云函数或同名方法是否存在”作为功能已实现的判断依据，而是把后端拆分为可独立验证的技术功能，逐项检查：

1. 技术方案要求实现什么。
2. 当前代码、配置和基础设施实际实现了什么。
3. 实现是否完整覆盖正常流程、异常流程、并发、幂等、安全和补偿。
4. 存在哪些未实现、部分实现或与方案冲突的内容。
5. 每个结论对应哪些代码或配置证据。
6. 缺口的风险等级、影响范围和建议修复顺序。

本检查阶段默认只分析和报告，不直接修改业务代码、配置、数据库或云环境。需要实施修复时，应基于检查结果另行创建开发任务。

---

## 2. 拆分原则

使用以下结构组织检查：

```text
业务功能域
  └─ 可独立验收的技术功能
       ├─ 接口与参数
       ├─ 数据读写
       ├─ 状态变化
       ├─ 事务与幂等
       ├─ 异常与补偿
       ├─ 安全与隐私
       └─ 测试证据
```

业务模块用于归类，可验收技术功能用于作出实现判断，横切能力用于防止遗漏。不能仅按文件、云函数或传统 Controller/Service/Repository 分层判断完成度。

一个检查项应足够具体，能够对应至少一种明确证据：

- 云函数入口或 type 路由。
- handler、service、repository 或公共 helper。
- 数据库查询、事务和原子更新。
- 集合字段、唯一索引或查询索引。
- 云存储路径及权限规则。
- 定时触发器和任务处理器。
- 环境变量或发布配置。
- 错误码及客户端契约。
- 自动化测试、集成测试或故障注入测试。

“安全可靠的图片上传”“完整实现图片管理”等包含多个判断的描述粒度过大，必须继续拆分。

## 3. 权威基线与冲突处理

执行检查前必须完整读取相关技术方案。若文档之间存在冲突，按以下优先级判断：

```text
TECHNICAL-ARCHITECTURE-图片笔记小程序-V1.0.0.md
  > TECHNICAL-DESIGN-图片笔记小程序-V1.0.0-P0问题修复.md
  > DATABASE-SETUP-CHECKLIST.md
  > PRD 及标签增量 PRD
  > 当前代码中的注释或旧实现
```

主技术架构已经合并 P0 修复时，以主技术架构为最终口径。发现架构、数据库清单和 PRD 仍有冲突时：

1. 不自行选择更容易实现的方案。
2. 在报告中记录冲突位置和两种口径。
3. 标记为 `BASELINE_CONFLICT`。
4. 说明冲突是否影响代码实现结论。

---

## 4. 实现状态定义

每个技术功能只能使用以下状态之一：

| 状态 | 定义 |
|---|---|
| `IMPLEMENTED` | 代码、配置、数据约束和必要测试均符合当前方案 |
| `PARTIAL` | 主流程存在，但缺少异常、事务、并发、安全、补偿或测试等必要部分 |
| `NOT_IMPLEMENTED` | 没有对应实现，或仅有空壳、TODO、模拟返回 |
| `DEVIATED` | 已有实现，但行为、数据模型或接口与当前方案冲突 |
| `UNVERIFIED` | 静态代码无法确认，需要云环境、控制台或运行验证 |
| `BLOCKED` | 缺少必要文件、依赖、权限或环境，无法继续分析 |
| `NOT_APPLICABLE` | 经基线确认该功能不属于当前版本或当前模块 |
| `BASELINE_CONFLICT` | 权威文档之间存在未解决冲突，无法形成唯一预期 |

不得因为存在同名函数、字段或注释而标记为 `IMPLEMENTED`。没有测试并不必然表示功能未实现，但高风险事务、并发和补偿逻辑缺少验证时，最高只能标记为 `PARTIAL` 或 `UNVERIFIED`，并说明原因。

---

## 5. 证据要求

每个非 `NOT_APPLICABLE` 检查项至少记录：

- 架构预期：对应文档章节或明确行为。
- 代码证据：文件路径和起始行号。
- 配置证据：索引、权限、触发器或环境变量位置。
- 测试证据：测试文件、用例名称或“未发现”。
- 判断理由：为什么得到当前状态。
- 缺口影响：会导致什么错误或风险。

证据必须来自实际文件内容，不得根据目录名、函数名或经验推断。引用代码时保持最小必要范围，不复制大段源码。

如果索引、数据库权限或定时触发器只存在于文档而不在仓库配置中，应标记为 `UNVERIFIED`，不能当作已部署。

## 6. 执行顺序

AI 工具应按以下顺序执行：

1. 读取本文件及全部基线文档。
2. 识别仓库技术栈、目录结构和项目级说明文件。
3. 盘点云函数、公共模块、数据库配置、存储配置、触发器和测试目录。
4. 先检查公共能力、数据库和存储基础设施。
5. 再按 §7 的功能域顺序逐项检查。
6. 对关键业务流程进行跨模块串联验证。
7. 对横切能力进行第二轮反向检查。
8. 生成差距矩阵和风险汇总。
9. 执行适合当前仓库的只读或非破坏性验证。
10. 输出检查报告，不直接修复代码。

推荐功能域检查顺序：

```text
公共能力与基础设施
  → 用户与身份
  → 图片上传
  → 图片查询
  → 图片删除
  → 后台任务与补偿
  → 标签
  → 备注
  → 账号注销
  → 前后端接口契约
```

| CLN-07 | 注销任务推进 | 阶段失败重试，完成前不解绑 |
| CLN-08 | 孤立引用清理 | note/photo_tags 的失效引用 |
| CLN-09 | 派生计数校正 | tag_count/photo_count 聚合修正 |
| CLN-10 | 有界执行 | 批次大小、最大扫描次数、超时续跑游标 |
| CLN-11 | 安全日志 | 只记录安全错误码和不可逆摘要 |

### 7.11 前后端接口契约

| 编号 | 技术功能 | 核心检查点 |
|---|---|---|
| API-01 | 上传协议 | 客户端使用 prepare/confirm/cancel，不传可信元数据 |
| API-02 | 上传任务恢复 | 保存 attemptId、expiresAt 和服务端 photoId |
| API-03 | 取消结果 | 正确处理 CANCELED 与已先确认的 CONFIRMED |
| API-04 | 图片分页 | 客户端使用 nextCursor，不使用 page |
| API-05 | 备注分页 | 客户端使用绑定排序参数的 nextCursor |
| API-06 | 删除状态 | 接受 PENDING/PROCESSING/RETRYING/COMPLETED |
| API-07 | 错误码 | 新旧错误码无混用，不再处理 TAG_ACCESS_DENIED |
| API-08 | 批量标签来源 | 只使用 confirm 返回的成功 photoId |
| API-09 | 兼容性 | 新旧客户端与云函数不会混合发布 |

## 8. 跨模块流程验证

完成逐项检查后，必须串联以下流程。任一环节缺失时，相关模块不能全部标记为 `IMPLEMENTED`。

### 8.1 上传成功

```text
prepare
  → pending 上传
  → confirm 租约
  → 文件真实性校验
  → 内容审核
  → active 提升
  → 配额/photo/attempt 原子事务
  → 返回唯一 photoId
  → pending 补偿清理
```

### 8.2 上传取消竞态

```text
cancel 先提交 → attempt=CANCELED → 迟到 confirm 不创建 photo
confirm 先提交 → attempt=CONFIRMED → cancel 返回原 photoId
```

### 8.3 图片删除

```text
delete 事务
  → photo=DELETING 且立即隐藏
  → STORAGE_DELETE
  → NOTES_CLEANUP
  → PHOTO_TAGS_CLEANUP
  → PHOTO_FINALIZE
  → 精确释放一次空间
  → task=COMPLETED
```

### 8.4 标签筛选

```text
校验本人 tag
  → relation cursor
  → 批量读取本人 ACTIVE photo
  → 跳过失效关系并继续扫描
  → 按 relation 恢复顺序
  → nextCursor 使用最后扫描的 relation
```

### 8.5 账号注销

```text
申请注销
  → user=DELETING
  → 拒绝普通业务接口
  → 分阶段清理全部存储和数据库数据
  → 标签及关系清理完成
  → 空间和用户数据完成
  → 最后解绑身份
```

## 9. 横切能力反向检查

模块检查完成后，必须使用以下问题对全部代码进行第二轮扫描：

1. 是否存在不带 `_openid` 的具体资源查询？
2. 是否存在先按 `_id` 全局查询、再判断资源归属的代码？
3. 是否存在不带 `photo.status = ACTIVE` 的图片业务读写？
4. 是否仍接受或信任客户端 `size/width/height/format`？
5. 是否存在“先查后写”但没有唯一索引兜底的幂等逻辑？
6. 是否把配额、photo 和 attempt 拆成多个独立提交？
7. 是否使用 `.skip()`、`page` 或加载全部关系后本地分页？
8. 是否存在只按时间排序、没有 `_id` 稳定第二排序键的列表？
9. 是否存在删除阶段重放后重复减计数或扣空间的路径？
10. 是否存在客户端可写 active 对象或直接读写数据库集合的权限？
11. 是否通过错误码、响应字段、日志或耗时差异泄露资源存在性？
12. 是否在日志中记录原始 OPENID、资源 ID、fileID、URL 或用户内容？
13. 是否存在没有租约、游标或批次上限的异步任务？
14. 是否存在异常后提前返回成功但权威状态尚未提交的路径？
15. 是否存在文档要求但没有代码、配置或环境验证证据的能力？

## 10. 风险优先级

| 优先级 | 判断标准 |
|---|---|
| P0 | 可能造成数据越权、空间超限、重复计费、数据丢失、不可恢复半提交或发布阻断 |
| P1 | 影响主要功能正确性、幂等恢复、删除完成、分页稳定性或重要验收 |
| P2 | 影响性能、可观测性、维护成本、次要异常体验或测试覆盖 |
| P3 | 代码质量、文档、命名和低风险一致性问题 |

一个缺口同时影响多个模块时，只建立一个主问题，并在“影响模块”中列出全部模块，避免重复计数。

## 13. 标准报告结构

AI 工具最终应生成独立 Markdown 报告，建议命名：

IMPLEMENTED /（总数 - NOT_APPLICABLE - BASELINE_CONFLICT）
